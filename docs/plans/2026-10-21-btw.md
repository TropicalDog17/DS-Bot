# Side chat

- Date: 2026-10-21
- Related: #407, #489

## Why

A Bot's work often takes minutes to tens of minutes. When the user wants to "ask one thing on the side", the normal input box belongs to DSH, and the message is queued or interjected according to the busy-Enter preference: a queued message is only read after the current turn ends; an interjection changes the Bot's current course; and both go permanently into the conversation history and are billed again on every later turn. Claude Code proved this need in 2026-03 with `/btw`: it answers with one independent, single-turn call without tools that uses the current Session's full context, does not interrupt the main task and does not write into the main conversation history. The request has the same shape as the Session's own requests, so it can reuse the prompt cache prefix (whether it hits depends on the provider).

The problem with single-turn cards: there is nowhere to ask a follow-up on the answer (a follow-up has to go to the main conversation), and the card sits between the Bot's messages, cannot be closed and takes up space. Side chat moves this into the Bot sidebar: a lasting "Side chat" view that can be opened several times, takes follow-ups and can be closed, and the main conversation no longer shows question cards.

Bots also need to "pull" facts in the other direction (I need a fact the other Bot has, while the team rule for `message_bot` is to "push"), but that line (`ask_bot`) changes the decided design for handing out work. It is a separate proposal and not part of this design.

Trade-offs:

- Side chat only answers and does not act. It runs no tools, cannot read new files and cannot change anything, so it is safe by nature.
- Each question takes a fresh snapshot: the answer is "based on progress so far", and steps in flight in the turn are not visible.
- Follow-ups rely on the chat's own history: the finished question-and-answer pairs in the same side chat are sent with the new question; failed and cancelled entries are not.
- It does not enter the history the model sees, but it leaves a trace in the interface: the user can always check what was asked and what was answered, so results can be checked.
- The request has the same shape as the Session's own requests (same route, same thinking effort, same tool declarations): this keeps the Session request's prefix and improves the chance of reusing the prompt cache, as the handoff note (`writeNote`) does.

## Decided behavior

### Snapshot

- Each question takes a new snapshot: the Session's request header at that moment (route and thinking effort), derived messages, tool history and Session identity, all taken together so the Session cannot change halfway through assembly. The snapshot holds the history committed to the Session; DSH persists with an asynchronous buffer, and the snapshot does not wait for it to reach disk.
- It only goes up to the boundary where "every tool call has a result": DSH commits the assistant message with tool calls first and runs the tools after, so the batch still running with results incomplete (together with that assistant message) is not in the snapshot. DeepSeek's adapter refuses a tool call history with missing results.
- Steps in flight outside the snapshot are not visible: the answer can lag behind what the Bot is doing, and the interface always notes this.

### A call without tools

- The request has the same shape as the Session's own requests: same route, same thinking effort, same tool declarations and tool history. After the snapshot, the messages carry the finished question-and-answer pairs of this side chat (in order), and the current question comes last. The output limit also follows the snapshot route's config: thinking and answer share the output budget, and a low custom limit often cuts a thinking model's answer off before it finishes.
- Because the tool declarations are included, the prompt states clearly "only answer, do not call any tools"; the host runs no tools: tool call blocks the model returns are never dispatched. One retry is allowed; if the second attempt still returns a tool call, it fails and the entry shows the reason. The retried call also counts toward usage.
- An answer that claims to have done something cannot be trusted (no tool is ever run); the top of the view always notes "Answered from progress so far; nothing was run".

### Side chats between the user and a Bot

- A Bot can have any number of side chats. `/side` or "Side chat" in the sidebar's "···" menu opens a new one; the sidebar's tab strip has one tab per side chat, clicked to switch, and each tab takes its first question as its title.
- `/side` is typed in the Bot's own chat, followed by the question; on submit, it asks the question and opens the panel to that chat: if the chat is still answering, it opens a new one; otherwise it continues the most recently updated one. It works whether the Bot is busy or idle.
- The entry goes through DSH's input trigger mechanism (the input trigger's `matchSpace`/`matchEnter`/`matchClaim`): the normal input box belongs to DSH and cannot be intercepted through DS Bot's own `api/bot` send path. Once claimed, it is accepted at once: the answer runs in the background, the input box does not stay in the submitting state, and the entry first shows "Answering…", then the answer fills in when it arrives.
- Input whose claim fails never falls through to a normal send. The following three cases are all refused after the claim (a refusal thrown by contract: the content of the input box stays as it is, and the reason is shown): typing `/side` in a group chat (side chat is only available in a Bot's own chat); input with attachments (attachments are not supported); `/side` with no question (the hint asks for a question).
- The answer uses the route and thinking effort in the snapshot, matching the request that produced this context. When the Bot has never run a model and the snapshot has no route, it refuses and asks the user to have one normal conversation first.
- A chat answers only one question at a time: while the previous one is still "Answering…", a question to that chat is refused with a hint to wait or cancel; in the interface the input box is disabled according to the entry's state.
- The view shows the question bubble, the answer (Markdown) and the status: "Answering…" with a cancel button; a failure shows the reason; a cancel shows "Cancelled".
- These questions and answers are not written into the Bot's history that the model sees: the main conversation context does not change, and the running turn is not affected and does not change course; the history used for follow-ups belongs only to this side chat and does not enter the main conversation.
- Side chats are stored per Bot in their own file, not in the team state file; the team view carries all chats of each Bot. There is no limit on the number of entries, characters or concurrent questions.
- An entry that is still answering can be cancelled: this aborts the call. Collapsing or closing the whole panel does not delete side chats (they are host data); closing a side chat's tab deletes it, together with its content in the file. After DSH restarts, unfinished entries it reads are marked failed.
- The calls count on the usage page with kind `side`; reaching the output limit marks the entry failed, keeps the part of the answer already produced, and notes that the answer was not finished because of the output limit.

### The old `/btw` cards

- The `/btw` command is removed, and typing `/btw` sends it as ordinary text. Existing question cards stay where they are, read only: a card from a closed turn hangs at the end of the turn, and a card whose turn is still open or cannot be found sits in the dock above the input box. The card header has a delete entry; deleting removes only that card and its stored record. Nothing is cleared or migrated automatically on upgrade.

## Not done

- Side chat is not open in group chats, and group Sessions are not snapshotted.
- Side chat does not run tools; to act, use the main conversation.
- The content of side chats is not written into the context the Bot's model sees, not written into memory, and not pushed to its turns afterwards.
- No side questions from Bot to Bot (`ask_bot`): it changes the decision in the handoff design that "asking without acting is left to a separate app". It is a separate proposal and needs the maintainer's confirmation.

## Known limits

- The snapshot only holds the history committed to the Session, cut at the boundary where "every tool call has a result"; steps in flight in the turn are not visible, so the answer can lag behind what the Bot is doing.
- Whether the prompt cache hits depends on the provider; the same shape can only keep the prefix and improve the chance of reuse. On a miss, one question costs the input of a full-context call; the answer's output and a possible retry are billed as usual.
- With tool declarations included, the model can still return tool calls: they are not run, there is one retry, and a second offence fails.
- Follow-ups only carry the finished question-and-answer pairs of the same chat; different chats know nothing of each other, and the snapshot has no other side chats.
- There is no total limit; usage stays visible through the usage page and the tabs.

## Changes

- 2026-10-21: first draft; first review round (tool-balance boundary for the snapshot, entry through the input trigger mechanism, meaning of the snapshot route, card truncation and cancel rules); second review round (request with the same shape as the Session to reuse the cache prefix, removed the thinking effort downgrade, three refusals after claim for group chat / attachments / empty question, at most 2 in-flight questions per Bot, Bot-to-Bot `ask_bot` moved out of this design into a separate proposal); third review round (a running turn has no turn-end slot, so the running card moves to the dock above the input box and returns to its place after the turn ends; old part cards join DS Bot's own rendering of old parts; the cache wording was toned down to "reuse the prefix, whether it hits depends on the provider", and "nearly zero cost" was removed; "written to disk" became "committed to the Session"; accepted at once after the claim, answered in the background). Waiting for an issue and a pull request.
- 2026-10-23: review feedback (#413): removed btw's custom output limit (2000 tokens) and used the route's own limit instead; thinking and answer share the output budget, and a low custom limit often made a thinking model's btw end in a truncation failure. The limit of 20 cards per Bot stays.
- 2026-10-23: removed the limits on the number of entries, characters and concurrent questions; cards are stored in files per part.
- 2026-10-24: /btw became Side chat in the sidebar (#489): `/side` opens a lasting side chat, a Bot can have several, managed with sidebar tabs; follow-ups carry the finished question-and-answer pairs of the same chat, and each question still takes a new snapshot; collapsing the panel keeps them, and only closing the tab deletes one; old /btw cards stay in place, read only.
- 2026-10-25: old /btw cards keep their content read only, but the user can delete them one by one (#550); old cards with nowhere to go no longer sit above the input box forever.
