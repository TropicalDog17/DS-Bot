# iOS build and TestFlight

- Date: 2026-11-13
- Related: issue #1448

## Why

v0.3.5 already has the Android mobile app (pair by scanning a QR code in Settings → Phone), but there
is no iOS version, so iPhone users cannot pair. iOS signing and TestFlight distribution need an
Apple Developer Program account. This note lists the steps for preparing the account, signing,
building and uploading; the account holder manages the account, payment and certificates.

## Current state

- `mobile/` is an Expo (React Native) project, one codebase for both platforms. The native iOS
  project is generated by `expo prebuild` and not committed (`mobile/.gitignore` ignores `ios/`).
- app.json already has the iOS settings: bundle id `io.github.fei2411.dsbot`, deployment target
  16.4, buildNumber following the version, `zh-Hans`, and the camera permission text.
  `mobile/app.config.js` writes the version from `ds-bot/package.json` as the iOS buildNumber.
- An unsigned simulator build has been checked (Xcode 26.6 + Expo SDK 58, `xcodebuild` BUILD
  SUCCEEDED, the app installs and starts in the iPhone simulator). The CI job
  `Mobile app iOS build (simulator)` runs this on every change, which proves that it compiles.
- The script for signing, archiving and uploading to TestFlight is in place
  (`mobile/scripts/ios-archive.sh`); only the Apple account and keys are missing.
- Installing on a real device and pairing by QR code are not done yet; they also wait for the
  account and a device.

## What the user does

Do these in order; what each step produces is needed later. All pages are on
<https://developer.apple.com> and <https://appstoreconnect.apple.com>.

1. **Enroll in the Apple Developer Program**: <https://developer.apple.com/programs/enroll/>. An
   individual account enrolls with an Apple ID and verifies its identity; an organization account
   also needs a D-U-N-S number. The fee is 99 US dollars a year, and the Account Holder does this
   personally.
2. **Accept the agreement**: App Store Connect → "Agreements, Tax, and Banking" → accept the Program
   License Agreement. A free app does not need the tax and banking details for paid apps.
3. **Get the Team ID**: developer.apple.com → Account → Membership details, find the **Team ID**
   (10 characters, letters and digits). It is not the same as the App Store Connect API Issuer ID.
4. **Register the App ID**: developer.apple.com → "Certificates, Identifiers & Profiles" →
   Identifiers → click `+` → App IDs → App:
   - Description: `DS Bot`
   - Bundle ID: choose **Explicit** and enter `io.github.fei2411.dsbot` (it must match exactly; no
     wildcard)
   - Capabilities: keep the defaults. The app uses the default keychain group of
     `expo-secure-store` and needs no extra capability; do not tick items it does not use, such as
     Associated Domains.
5. **Create the App Store Connect record**: appstoreconnect.apple.com → "Apps" → `+` → New App:
   - Platform iOS; name `DS Bot` (it must be unique on the App Store; if it clashes, use another,
     for example `DS Bot Team`)
   - Primary language as needed; Bundle ID: the one from step 4; SKU: a string nobody has used (for
     example `dsbot-ios`)
   - User access can stay at the default
6. **Generate an App Store Connect API key**: App Store Connect → "Users and Access" →
   "Integrations" → App Store Connect API → "Team Keys" → `+`:
   - Name for example `dsbot-ci`; access **App Manager** (can upload and manage builds; Admin works
     too)
   - After generating, `AuthKey_<KEYID>.p8` **can be downloaded only once**. Also note the **Key
     ID** in the list (10 characters) and the **Issuer ID** at the top of the page (a UUID)
   - If "Integrations / Team Keys" is not visible, the account's role is too low: an Account Holder
     or Admin must create it
7. **(Optional) Apple ID for testing**: TestFlight internal testing invites Apple ID email
   addresses. Give the email of the Apple ID used on the iPhone that will test.

### What the user hands to us

| Item | Where to get it | What we use it for |
|---|---|---|
| Team ID (10 characters) | developer.apple.com → Account → Membership details | Signing settings (`DS_BOT_APPLE_TEAM_ID`) |
| Issuer ID (UUID) | Same → Integrations → top of the App Store Connect API page | API authentication (`APPLE_API_ISSUER`) |
| Key ID (10 characters) | Same → Team Keys list | API authentication (`APPLE_API_KEY_ID`) |
| `AuthKey_<KeyID>.p8` file | Downloaded when the key is generated (only once) | API authentication (`APPLE_API_KEY` points to it) |
| The App record already created (matching Bundle ID) | App Store Connect → Apps | The target app for TestFlight uploads |
| (Optional) Apple ID emails for internal testing | — | TestFlight test invitations |

Do not paste the `.p8` or the Issuer ID into a chat, an email or an issue. Use a secret card
(`request_secret`), or put it in a folder on the machine and tell us only the path. The repository
stores no keys.

## What we do once we have them

1. Place the key: on the machine, put it at `~/Library/private_keys/AuthKey_<KEYID>.p8` (or any
   path, pointed to with `APPLE_API_KEY`); CI uses a secret, never the repository.
2. Set the environment variables (pass only the names, not the values):
   ```sh
   export DS_BOT_APPLE_TEAM_ID=<Team ID>
   export APPLE_API_KEY=$HOME/Library/private_keys/AuthKey_<KEYID>.p8
   export APPLE_API_KEY_ID=<Key ID>
   export APPLE_API_ISSUER=<Issuer ID>
   ```
3. Build: `cd mobile && sh scripts/ios-archive.sh`. The script runs `expo prebuild` → `pod install`
   → an archive signed automatically with the API key → exports `mobile/ios/build/export/DSBot.ipa`.
4. Upload: `sh scripts/ios-archive.sh --upload` uploads to App Store Connect with
   `xcrun altool --upload-app`. After the upload, wait for processing to finish, then add internal
   testers in TestFlight (at most 100).
5. TestFlight settings: App Store Connect → the app → TestFlight. Internal testing needs no App
   Review; external testing needs Beta App Review. Export compliance: the app's connection layer uses
   standard algorithms for end-to-end encryption, and Info.plist declares
   `ITSAppUsesNonExemptEncryption=false`; if review asks, explain it as standard algorithms (X25519
   and so on).
6. Version numbers: `CFBundleShortVersionString` follows the version in `ds-bot/package.json`; the
   build number is the same by default. To upload the same version again, set
   `DS_BOT_IOS_BUILD_NUMBER` to a build number higher than the last one and run the script again,
   without changing the product version. Build numbers are 1 to 3 parts of plain digits, for example
   `0.3.7`, `0.3.8`. See
   [Apple's CFBundleVersion format](https://developer.apple.com/documentation/BundleResources/Information-Property-List/CFBundleVersion).

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `No signing certificate "iOS Distribution" found`, `No profiles ... were found` | Not all three `-authenticationKey*` arguments were passed, or the account has not accepted the agreement, or the key's access is below App Manager. Automatic signing needs the app's record to exist in App Store Connect (step 5) |
| `Authentication failed` / HTTP 401 | The Key ID, Issuer ID and `.p8` are not from the same key, or the key was revoked; generate a new one |
| `bundle identifier ... is not available` / App ID does not exist | The App ID is not registered or is misspelled; `ios.bundleIdentifier` in `mobile/app.json` must match the App ID exactly |
| Upload fails with `ITMS-...` | Usually the build number was not raised, the version is a duplicate, export compliance is missing, or there is an icon or privacy manifest problem; read the full error in the altool output |
| `pod install` fails | Run `pod repo update` first; CI uses the CocoaPods that comes with the macOS runner |
| The CI iOS job fails but the local build passes | The unsigned simulator build only proves that it compiles; for signing problems, read the local archive output |

## Not done

- Before the account exists: no TestFlight upload, no faked signing, and no certificates or
  placeholders in the repository.
- No App Store release (store text, screenshots, review submission); that comes after TestFlight.
- No iPad-specific layout; the existing Android flow does not change.

## Known limits

- TestFlight: at most 100 internal testers; each build lasts 90 days; external testing needs Beta
  App Review.
- Account roles: only an Account Holder or Admin can create Team Keys; only the Account Holder can
  sign agreements.
- The CI iOS job only does an unsigned simulator build. A signed build needs the account and keys
  and goes through the local script or a release flow with secrets.
- Checking QR pairing on a real device still waits for the account and a device (the simulator has
  no camera; the app has a way to paste a pairing link, but that does not replace checking on a real
  device).
