## Why

### Who uses it

Windows is the main platform of the desktop app. Across the installer downloads of the three releases 0.2.0 to 0.2.2, Windows has about 3850, macOS about 1900 and Linux about 250 (GitHub download counts, auto-updates included). These Windows users almost never open issues: of 259 issues, only about 3 can be traced to the Windows desktop app. On the other side, 10 different users reported "the first message fails / no reply". Most people give up quietly along the way.

The typical user: Chinese interface, maybe not a developer, maybe in mainland China (GitHub is slow or blocked), maybe without a DeepSeek account or API key yet, maybe never used DeepSeek Harness (DSH).

### How long the road is today

On 2026-10-26 we tested on `dev` as a brand-new user: a throwaway home folder, data location and shell data, no key in the environment, Chinese interface. The test used unpackaged Electron and `DS_BOT_HOME`, so the rows below for download, install, the first-start dialog, import, start failure and uninstall come from the code, CI and user reports; the other rows were tested.

Also, when the "Downloads" folder cannot be resolved (deleted, or redirected to a place that is not available now), `app.getPath('downloads')` (called by `main.mjs` when it builds the window) throws: the window never shows, and after up to 15 seconds "DS Bot couldn't start" appears with Electron's English error, then the app quits. We reproduced this throw on Electron 44.

With a key already in hand and no DSH team, the fastest path still takes: two SmartScreen clicks, two clicks in the install wizard, one system dialog, a 13 to 21 second wait, then "Continue → Add API key → paste → Save and continue → pick a model": 10 steps in all before the first reply; with a DSH team up to 13 steps. Without a key, the user also has to leave the app to get one.

### Root causes

1. **The first start asks questions in the shape of the implementation.** The data location, the team workspace and DSH's profiles are implementation concepts, yet a system dialog asks the user about them before there is a window.
2. **There are three entrances for connecting a model, repeating each other, none complete.** DSH Web's own two-step guide, plus Chief's card. None says how to get a key, that it costs money, or whether the key works.
3. **Failures give no next step.** Credential errors show the raw text, a start failure shows an English box, an import that meets newer chats is a dead end, and the import gets only one chance.
4. **Distribution relies only on GitHub, unsigned.** Download and auto-update both go through GitHub, SmartScreen and Smart App Control keep people out, and the release page does not say which file to download.
5. **Nobody catches the pitfalls of the first hour.** The Windows-only sandbox start failure, the system proxy, the "Downloads" folder, plus the cold start that shows no Bot on every platform (#559, reported on Windows) and the long part change after an import (#384).

### Trade-offs

- **One guide surface per stage; what it shows depends on state, with no stored "done" flag.** Before the engine is up, the guide surface is the app's own start page; after the engine is up, it is the setup card in the Main Bot's chat. A skipped step is not recorded anywhere; while its condition holds, it comes back by itself next time. The onboarding in section 6 stores no flag either: it is over when the Main Bot's Session has the grey "Onboarding done" line or a message the user sent; the grey line that "Skip setup, start now" writes is its only record (section 8).
- **The model is connected in a chat card, not in a separate welcome wizard in the app.** The setup card is plugin code, so users in DSH Desktop and DSH Web benefit too; another wizard in the app would mean maintaining two. The start page only lets people see that it is moving and how far it has got: the three arcs around the whale are the three stages; it stays silent when all goes well and only speaks a line when the user needs to know something or answer.
- **The model only starts to help once it is "connected".** The order cannot be reversed: the engine writes the key into its own `DSH_HOME`, and the engine's Host handles the DeepSeek sign-in callback, so the engine must first run on some data location; `importTeam` refuses a location that already has Bots, and the copy replaces the whole `bot/` and restarts the engine, so a key entered first would also override the imported key and sign-in. So location, import and connecting a model stay cards. The model beats a card in only two places: turning the user's sentence into Bots with names and roles, and the free first task. It is also slower, costs money first, and words things differently every time, so every step keeps a card that works without the model, and the limits are mechanisms in code, not prompts (section 6).
- **Fix the quiet losses first.** The download page, the trust notes and the one-click install are the cheapest and reach the most people. Signing and a mirror in China wait on outside approvals and accounts, so they start first.
- **Do not change DSH.** Use only documented switches and slots. DSH's "Preview notice" has no documented switch, so we file a request with DSH; until then the user clicks "Continue" once after entering. We do not pretend to be `dshDesktop`.

## Decided behavior

What follows is the new flow. The source language of interface text stays as it is: the plugin is English plus the Chinese in `i18n.js`, and the app's main process uses its own Chinese and English table; only one language is listed here. `{name}` in the copy is the Main Bot's name. The few places marked "open" are written as the suggestion in "Open questions" at the end; once decided, they change to the decided option.

### 1. Download

- The top of `README.md` is a bilingual Chinese and English download block (GitHub shows the English README by default): Windows 10/11 (64-bit), about 212 MB, two direct download links "Mirror in China (recommended)" and "GitHub". Until the mirror passes its checks, only the GitHub link is there, never a dead link.
- Right after the download block it says plainly: double-click to install, and it opens by itself when done; no admin rights, no separate Node or DSH needed; you need a DeepSeek account (you can sign up on the spot with a phone number) or a DeepSeek API key; DeepSeek charges by usage, about this much per round of chat (measured from three first-task turns on the default model, with a link to DeepSeek's price page); DS Bot is a community open-source project, not an official DeepSeek product.
- Until the installer is signed, the download block has trust notes (text plus our own drawings, no screenshots of Windows or other products):
  - Edge says the file "isn't commonly downloaded": "···" → "Keep" → "Show more" → "Keep anyway".
  - "Windows protected your PC": "More info" → "Run anyway".
  - "Smart App Control blocked…" with no "Run anyway": there is no safe way around this for an unsigned installer; use DSH Desktop with the DS Bot plugin instead. Do not turn off Smart App Control.
  - Antivirus software blocks it: first check with `certutil -hashfile <file> SHA256` against `SHA256SUMS.txt`, then choose "Trust".
  - The installer says uninstalling the old version failed: first close DS Bot; when antivirus software blocked the installer, check it as above, choose "Trust", and run the installer again.
- Every Release's notes start with a `下载 / Download` ("Download") table generated by CI: Windows first (mirror in China, GitHub, size, "double-click to install"), then macOS (Apple silicon / Intel) and Linux (AppImage / deb); below the table a note says that `.blockmap`, `latest*.yml`, `ds-bot-*.tgz` and the source code are for auto-update and the plugin, and need not be downloaded. Only then the changelog.
- A Release carries files without a version number (such as `DS-Bot-win-x64.exe`) and `SHA256SUMS.txt`. Until the Release marked Latest carries these files, the fixed links under `releases/latest/download/` return 404, so the README first links to the `releases/latest` page; the fixed links (which skip the file list) ship with the fixed-link check in M3. The plugin install line in the README does not name a version either (today the README still says `ds-bot-0.2.1.tgz`).
- The release order is "package (→ sign) → upload to GitHub and the mirror → write the download table → publish to npm → mark as Latest last", so a Release is never Latest while its installer only arrives minutes later. Today the workflow is triggered by `release: published`; without a public Release there is no tag, and the workflow needs the tag to check out the code and to check that it is on `main`; npm's Trusted Publishing is also bound to `release.yml`. So the starting point is that the maintainer publishes without ticking "Set as the latest release", and the last step of the workflow runs `gh release edit --latest`; npm publishing stays in `release.yml`.
- A new "Install problem" issue form: it asks for no diagnostics (the app did not even run), only the system version and display language (mostly Windows; install problems on macOS and Linux use this form too), the step where it got stuck, and the text of the dialog or a phone photo of it.

### 2. Install (one-click install open)

- After the double-click there is only a small window "Installing DS Bot, please wait…" with a progress bar, about 30 seconds, no pages to click. It installs for the current user only, into `%LOCALAPPDATA%\Programs\DS Bot`, without admin rights. It creates desktop and Start menu shortcuts "DS Bot" and opens the app when done.
- Users who want another program location use `/D=` (in the advanced notes of README.md); the data and the team workspace can already go on another drive.
- Installer languages `[en_US, zh_CN]`: Chinese Windows gets Chinese, other languages get English (today other languages fall back to Simplified Chinese).
- A one-click upgrade over an old wizard install in a custom folder keeps that folder (checked in CI).
- Once signed (route open), the publisher shows the signing subject; set `publisherName` so that `electron-updater` checks the signature of later update packages.
- A few NSIS errors built into electron-builder (uninstalling the old version failed, extraction failed) have no Chinese and stay in English. We do not redefine them in `installer.nsh`: electron-builder treats NSIS warnings as errors by default, and a duplicate definition fails the build. The Chinese translation goes to electron-builder.

### 3. First start: the start page

- The window comes first. Within about 1 second of the process start, the start window shows the app's own local page (`app/src/start/`): frameless as now, a 40 px title band that can be dragged, the system buttons at the top right, Mica on Windows 11. The start page is in a separate start window, and the engine's page loads in a hidden main window ([Start window](2026-10-26-start-window.md) section 1, open). During the whole start, cards and failure pages included, the start window is 720 × 540 (720 × 500 when the work area is short); it changes size only once, at the handoff: it grows into the main window's rectangle, and the main window appears on the same rectangle (same note, section 8).
- **The ring is the progress.** The start page shows only the Main Bot's whale (112 px), floating on a short waterline, inside a ring of three arcs, one per real stage: "Prepare the data folder" → "Start the local engine" → "Open the team". The arc in progress turns light blue with a glint running along it, and in front of the whale there is a small prop drawing what this stage is doing (a folder flipping pages, gears meshing and turning, little members jumping up); a finished arc fills clockwise, a stuck arc turns red; when ready, the three arcs join into a full ring. No title, no stage names, no explanation: the stage names are for screen readers only, in an invisible list "Start progress" (`aria-current="step"`), and the live region still says "{phase}: in progress" and "{phase}: done". Clicking the whale makes it spout water. The layout, the ring and the whale's moves are in [Start window](2026-10-26-start-window.md) sections 2 and 3.
- **Text only when it matters.** Only low disk space and errors bring text: on an error the whale says a line (centered below the ring, one line, no wrapping), and every error page has [Copy details] and [Save log…]; on low disk space the hint row has its line for the first 10 seconds, and the location row is at the bottom. Slowness brings no text either, only the whale's pose. The text of the first start:

| When | The whale's line | Hint row |
|---|---|---|
| When all goes well: entrance, the three stages, ready | none | none |
| Low disk space and no better drive | none | for the first 10 seconds "Only 1.2 GB left on drive C" |
| 45 seconds, the engine is not up yet | none (the whale switches to thinking) | none |
| 180 seconds | "This is taking too long. Try again?" | none; the card has only [Keep waiting] [Try again] [Copy details] [Save log…] |
| Start failed, the team view did not load | "DS Bot couldn't start", "The team view didn't load" | none |
| With a card | empty; the card says it in its own first line (15/20, 600, above the decided text): the recommended drive "Drive C is a bit full" (low space) or "I'm not allowed to put things here" (no write permission), the "It will go in…" card "I added one more folder", the rejected one "That place won't work", the missing data folder "Your data isn't where it was"; the import cards are in section 4; failure cards have none | hidden |

- When the whale's line changes, it fades out and in, .16 s each, without a queue. A failure draws no cross: the whale's failure pose, the red arc and the line are the failure. When the whale sinks and starts again in a new folder, the three arcs start from the beginning. When ready, the remaining arcs fill, the ring closes, the whale spouts once, jumps out of the water and lands on the Main Bot's avatar in the sidebar; with nowhere to land it dives (start window section 8).
- **Usually it asks nothing** and uses the default location, but the page says where it goes and that it can change: one line at the bottom center "Data on drive C, 412 GB free" and a grey [Change the location…] ([Start window](2026-10-26-start-window.md) sections 2, 4 and 6). If nothing is clicked, it goes ahead with it; only [Change the location…] opens the picker, the root is set as in "One location" below, and once set, the engine starts again in the new folder and the whale sinks and starts over (start window section 7); the folders created at the default location this time are deleted. A reinstall has no such line, and it folds away after an import has finished copying. First check whether this is a reinstall (next item), then whether a location card is needed. The only card for choosing a location is the recommended drive; its buttons have all passed a test write, so a click is never rejected afterwards; every card says where to change it later:
  - The drive with the data has less than 5 GB (with a team to import, less than "5 GB + the extra space the import card shows"), and there is a better drive: "Only 1.2 GB left on drive C. Put it on drive D (412 GB free)?" [Put it on drive D] [Keep it on drive C], with a small link "Another location…" at the end of the button row. Enter means put it on drive D. Without a better drive there is no card, only one line in the hint row "Only 1.2 GB left on drive C", and the start goes on.
  - The default location cannot be used (no write permission): the first sentence becomes the reason "DS Bot can't write files in `C:\Users\<user>`.", the second sentence is the same; the only buttons are [Put it on drive D] and the small link "Another location…", without [Keep it on drive C]. With no drive to recommend, there is only [Choose another location…].
  - The saved data folder is gone (mostly on later starts): "Can't find the data folder `D:\DS Bot\data`. The external drive may be unplugged, or the folder was moved or deleted. The old data won't be changed." [Try again] [Find it again…] [Start with a new blank team…]. [Find it again…] does not follow the root rules: when the chosen folder itself, or the `data` under it, has the `.ds-bot` marker and `bot/state.json` (so `~/.dsh` never counts), and it passes the location rules (not in DSH's home, not in the program folder), it is written as the data folder; when there is a `workspace` next to it, the team workspace moves there too, otherwise it stays. Otherwise the card says "There is no DS Bot data here.", and [Find it again…] stays.
- **A reinstall asks nothing.** When no location is saved and `C:\Users\<user>\.ds-bot` has a team (after a reinstall, or after `%APPDATA%` was cleared), it simply goes on with it: no recommended-drive card; low disk space only gets one line in the hint row "Only 1.2 GB left on drive C", and moving is in Settings → General → Location → [Move to…]; if it cannot write there, the recovery page comes straight up. The start page does not mention the last team or path; after entering, it is just there. The start page does not know the team workspace the old team registered: after the plugin starts it reports it once via `teamWorkspaceChanged`, and the app writes it as `workspace` in `locations.json`. Those who want a blank team go to Settings → General → Location → "Start with a new blank team…". Only the default location is recognized: old data kept elsewhere without a saved location is not found, as today.
- **How the recommended drive is chosen**: it is looked up once only when the drive with the data is below the threshold (5 GB, plus the extra space when there is a team to import: chats 1.2 GB plus the 3.4 GB of work files copied by default, so below 9.6 GB), or when the default location cannot be used (not when a reinstall goes on); a normal start does not look. This step comes before the engine warms up, so a migrating user first sees the recommended-drive card, then the import card. It reads `Win32_LogicalDisk` and `Get-Partition | Get-Disk` with the full path `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe -NoProfile -NonInteractive` (`windowsHide`, 5-second timeout): only fixed drives (`DriveType` 3) whose `FreeSpace` is not empty and whose bus is not USB, SD, MMC or a virtual disk, then confirmed once more with `fs.statfs`. With low space it excludes the drive the data is on now; when the default location cannot be used it may recommend `X:\DS Bot` on the same drive. It takes the one with the most free space, and at least 20 GB. When `X:\DS Bot` already exists, it is judged by the root rules below, and the drive is not recommended if it cannot be used. The test write only creates the missing levels and deletes what it created afterwards. If PowerShell fails, times out or is blocked by policy, it counts as no better drive. macOS and Linux recommend no drive; low space only gets one line in the hint row.
- **One location.** When changing the location, the user chooses only one folder, and the root `R` follows from it: for a drive root, `R` is the `DS Bot` under it; for a folder that does not exist or is empty, `R` is that folder; for a folder that was a DS Bot root before (its `data` has the `.ds-bot` marker, with no team or only a blank team that never talked), `R` is that folder too; for any other non-empty folder, `R` is the `DS Bot` under it. When `R` already exists, is not empty and is not a former root, it cannot be used. The data goes in `R\data` and the Bots' files in `R\workspace` (subfolder names open); the two are siblings and contain neither each other, just like the default `~\.ds-bot` and `~\DS Bot` are siblings under the same parent, and all rules stay the same. [Put it on drive D] means `D:\DS Bot\data` plus `D:\DS Bot\workspace`. The default install paths do not change (open). Settings has one place too: the "Location" row shows both paths, and one [Move to…] moves them together (section 8); those who want them apart do it under "Advanced".
- Only "Another location…" opens the picker, attached to the window, starting at the recommended drive, or without one at the parent of the current data folder. After the choice it first sets the root, checks both `R\data` and `R\workspace` against the current data folder and team workspace with the location rules, then does a test write. If all pass: when `R` is the folder the user chose, it is used directly with no confirmation; when the app added a `DS Bot` level, the same card becomes "It will go in `D:\DS Bot`." [Continue] [Choose again…]; it confirms only when the app changed the path the user chose. If it fails (no write permission, in OneDrive, `R` is someone else's non-empty folder, in DSH's home, in the program folder), the card gives the reason in one sentence, [Choose again…] is the main button, and the [Put it on drive D] [Keep it on drive C] of the card it came from stay; cancelling the picker goes back to that card. The DSH data rule is checked only when the folder really exists. "Change the location…" in the location row takes the same path without a card to come from: cancelling goes back to the location row, and an "It will go in…" or "That place won't work" already shown is withdrawn. Choosing the current root or data folder counts as no choice; a place inside the current data folder is not allowed; while the team workspace is still empty, it can become the new root.
- The location check of the first start and "Move to…" check the root with the same rules: not a whole drive, not someone else's non-empty folder, plus one test write.
- `locations.json` is written only after the engine starts successfully for the first time (`ready`) and the import question is answered. A UTF-16LE `locations.ini` is written at the same time for the uninstaller to read. A data folder the app creates itself gets a `.ds-bot` marker that holds no secrets; this marker is written when the folder is created, not at `ready`: if the app quits before the first start finishes, the folder it left is recognized next time as its own (the "former root" in the root rules) and is not taken for someone else's non-empty folder. The rule "nothing is recorded if the first start does not finish" stays: what is recorded is only `locations.json`. Every start first deletes the staging left from last time (its path is recorded in `%APPDATA%`, plus every `.import-*` and `.import-check-*` in the data folder).
- Then the engine's page loads: DSH's "Preview notice" → "Continue". DSH's own "Get started" and "Add an API key" no longer appear by themselves: in its own profile patch (passed through `runProfile`'s `patchFiles`, like `search-patch.mjs`), the app sets `credentialOnboarding: false` on `ui-settings-models`, which is a documented DSH setting. The patch replaces the whole `config` of this row, so every time the pinned DSH is upgraded, this row is rewritten against the new version. The app's patch holds only this row.
- **On a start failure**, the start page turns into the recovery page on the spot (no more waiting for GitHub, hiding the window or an English "Error" box): the whale's line says "DS Bot couldn't start" (the stuck arc turns red), with no jokes, followed by one sentence with the matching reason (no permission to write / not enough disk space / program files are incomplete, antivirus software may have blocked some of them / the local engine stopped halfway through starting / the data folder can't be found, the external drive may be unplugged / something unexpected happened) and one sentence on what to do; every kind gets [Try again] [Change the location…] [Start with a new blank team…] [Open the log folder] [Copy details] (changing the location follows the root rules of section 3 and moves the data and the team workspace together, with the moving rules of section 8: a rename on the same volume, copy and then delete the old one across volumes; with no team yet it just switches to another empty folder), plus a collapsible "Details" area (the last 200 lines of the log, redacted).
- When the start takes more than 180 seconds: the whale asks "This is taking too long. Try again?", the card has only [Keep waiting] [Try again] [Copy details] [Save log…], and the engine keeps starting meanwhile.
- When the background updater has found a new version, the recovery page shows "DS Bot {version} is out and may fix this." [Download and install], with the download percentage and "Download too slow? Download manually" (opens the mirror page).
- When the engine is up but the DS Bot view does not report ready within 20 seconds (ds-bot calls `dsBotApp.ready()` after the view has mounted): back to the start page, showing "The team view didn't load" [Reload] [Copy details] [Save log…].
- Double-clicking the icon again during the first start: restore and focus the existing window, on the failure page too.
- Building the window no longer depends on the "Downloads" folder: its location is read only at each download; if it cannot be read, the home folder is used, and failing that there is no default location and the user chooses.
- Log: `%APPDATA%\DS Bot\logs\main.log`, 2 MB × 3 rotated files, holding the output of the main process and the engine; before writing it strips `token=…`, `sk-…` and the query part of `/oauth/callback?…`, and replaces the full path of the user folder (such as `C:\Users\<user>`) with `%USERPROFILE%`.
- The start page is plain DOM with CSP `default-src 'self'`; its colors take the values of the DeepSeek theme in [UI standard](../design/ui-standard.md) section 2.1, and its font sizes the standard's 13 / 14 / 15 px. It gets only `dsBotStart` (`onState`, `act`), exposed only when the page address is exactly the start page file.   - Where the sign-in window comes from: on the click, DSH's web front end first does `window.open` of an `about:blank` (and sets its `opener` to null), and once it has the authorization link it sends it there with `location.replace` (today the app hands this step to the system browser). This blank window cannot serve as the sign-in window: Chromium creates a window opened by `window.open` in the session of the page that opened it (the main window's default session, stored on disk), the webPreferences of `about:blank` are copied from the main window too, and `overrideBrowserWindowOptions` cannot change the partition. So the app allows it through today's `setWindowOpenHandler`, keeps it hidden all the time, and treats it only as the handle in DSH's hands; on its first navigation (the main frame's `will-navigate` or `will-redirect`) the app stops that navigation: if the path is `/dsh/authorize`, the app creates its own sign-in window with this address; if not, it hands it to the system browser as today and destroys the blank window. DSH only ever sends it to a link with this fixed path on its own `platformOrigin`, so the origin of the authorization page is taken from this navigation, not read from DSH's configuration, and CI's loopback fake platform needs no extra setup.
  - The sign-in window is a child of the main window (`parent` is the main window): system frame, a fixed title "Sign in to DeepSeek" that does not follow the sign-in page's title (it stops `page-title-updated`); content area 480 × 680, and when the work area of the display holding the main window is less than 760 high, the height becomes the work area minus 80 and the sign-in page scrolls in the window; centered on the main window and wholly inside the work area; it cannot be minimized or maximized on its own, and minimizes with the main window. `sandbox`, `contextIsolation`, no preload, Node or webview; it uses a separate non-persistent partition (`deepseek-login`). Such a partition only goes away when the app quits, so every window close clears its storage and cache (`clearStorageData`, `clearCache`): the app does not keep the DeepSeek platform's sign-in state, the next sign-in does not carry the last account, and the sign-in token lives only in the engine's credentials. A new sign-in window waits until the previous window's cleanup has finished: every sign-in uses the same partition, and in a window opened before the cleanup is done, the cookies just received would be cleared too. Like the Bot browser's partition (`#configure` in `bot-browser.mjs`), this partition refuses permission requests, permission checks, device permissions and screen sharing, and cancels downloads; but it does not copy its `onBeforeRequest`: that rule blocks every request to the engine's local address, so the callback could not get through. The sign-in window's session uses its own `onBeforeRequest`: of the requests to the engine's local address (any local host name plus the engine's port), only the main frame's `GET /oauth/callback` passes; subframes, scripts and other paths are all blocked, so neither the sign-in page nor its captcha and QR frames can touch the engine. The window starts hidden and shows when the authorization page first paints (`ready-to-show`). All of these are documented Electron APIs, and nothing touches DSH.
  - Allowed addresses (only for navigations and redirects of the main frame, by `isMainFrame`; subframes in the sign-in page, such as captcha and QR, load and navigate as usual): the origin of the authorization page; https pages whose host name is `deepseek.com` or ends in `.deepseek.com`; the engine's local address with the single path `/oauth/callback` (DSH's callback). A `window.open` in the window (including links such as the user agreement and the privacy policy that the sign-in page opens in a new window) opens no new window; it always goes to the system browser, and the sign-in window stays on its page: the sign-in window has no Back, so opening it inside would leave no way back to the sign-in page. You'll come back here by yourself once you're signed in; don't close this window until then.", with the expiry time, [Cancel] and "Copy the sign-in link" as before, and after the sign-in it calls `dsBotApp.focus()` to come to the front. A sign-in runs in only one place at a time.
  - As soon as the callback has a response, the app closes the window without loading the response page (it watches the response of the `/oauth/callback` request with `webRequest` on the sign-in window's session, whatever the status code). A response does not mean the sign-in succeeded: the app's page has no `dshDesktop`, so DSH responds as for the web version: on success a 302 to the done page, by which time the engine has recorded the sign-in; when the exchange fails, a page that closes itself (200); on cancel 204; for a void or repeated callback 410. Whether the sign-in succeeded is read only from DSH's sign-in state, and the card follows that. On seeing the response, the app first records that this window's callback has had a response, then closes the window; this close counts as the app's own, and no `onClosed` is sent. Any later `did-fail-load` from this window (such as `ERR_BLOCKED_BY_CLIENT` caused by stopping the response, or an empty error page for 400 or 410) does not count as a sign-in page load failure.

For people who imported a team, the key has usually been copied along with `.credentials.yaml` or `.env`, and the setup card does not appear; when the imported key fails the check, the setup card comes back, and if the key found is the same as the one already stored in the data location, the row does not appear. Read only, never written, as with the import.
  - The clipboard holds exactly one DeepSeek key (after trimming leading and trailing whitespace, `sk-` plus 32 hex digits, the same rule the chat card below uses to recognize the DeepSeek format, to be confirmed by testing): the row says "There's a key on the clipboard: sk-1a2b3…". Keys in other formats get no row, so another provider's key is never sent to `api.deepseek.com` for checking. It is read only while the setup card shows: once when the card appears, and again every time the window comes back to the front; only the format is compared, nothing is recorded; the whole value stays in the app, and the page only gets the source and the first eight characters; when a later read finds the clipboard changed (the window comes back to the front, [Use this key] is clicked), the row is replaced by the new result or disappears.
  - With keys in both places there is still only one row: the app compares the whole values in the main process; if they are the same, only the DeepSeek Harness one counts; if different, it shows the clipboard one, with a small line below "Use the key in DeepSeek Harness instead (sk-1a2b3…)".
  - The first eight characters are as many as DSH's mask keeps. The app hands the value to the page only on the button click: `dsBotApp.foundKeys()` returns only the source and the first eight characters, and `dsBotApp.takeKey(source)` reads again and returns the whole value only when what it reads is still a key with the same first eight characters as the row; otherwise it returns no value, and the row is replaced by the new result or disappears. The page takes exactly the same check and save as a pasted key (the Host's `provider-key`). 401 or zero balance are handled as above, with the source named in the message: "The key in DeepSeek Harness doesn't work (401).", and the row disappears. For a key that failed the check (401), the plugin records its source and first eight characters in the page's memory (the app does not know the check result and gets no extra interface): later reads of a key from the same source with the same first eight characters in this page (the window comes back to the front, switching to another Bot and back, the card reappears) bring no row; with keys in both places, it offers the other one instead. The row only appears again after the page reloads.
  - `DEEPSEEK_API_KEY` in the environment needs no button: the engine inherits the app's environment (`process.env`), and when `.credentials.yaml` in the data location lacks this key, DSH's credential layer falls back to it, `describe` reports it configured with `source` `env` (`writable` still `true`), and the setup card does not appear; only when it fails the check does the "from the environment variable" card above appear. A key saved here goes into the credentials file and takes priority over the environment variable, so after [Try another way], pasting or signing in both connect without changing the environment variable.
- **A key pasted into the chat is recognized too** (all forms): real users paste their key straight into a Bot's chat box, and once sent it is in the chat record and also goes to the model. While there is no usable model, the Bot chat's input is already locked (see "the input is unavailable" below), so it cannot be pasted there; this card therefore covers Bot chats and group chats after a model is connected (for example when the user sends a new key while a fix card reports AUTH; a new team's Main Bot waits for the onboarding to end, and a key pasted into the goal card's input during onboarding is in section 6), and the moment before the model list has come in. The plugin watches the draft of every Bot and group chat Session (DSH's documented `ctx.conversation.input`, the `state` of each conversation); when the whole draft, trimmed of leading and trailing whitespace, is exactly one key starting with `sk-` (`sk-` followed by 20 or more letters, digits, `_` or `-`, at least one of them a digit, matching the rule DSH's mask uses to recognize `sk-` keys; other providers' `sk-` keys count too; other formats DSH's mask recognizes, such as `ghp_` and `AKIA`, are not model service keys and are not stopped; drafts with `NAME=` or quotes are not stopped either, like a key inside a sentence), it attaches a `ComposerBlock` to this conversation (DSH's documented `ctx.conversation.blocks`: the input turns grey, can be neither edited nor sent, and the draft stays in it), and shows a card in the card slot above the input (`conversation.input.dock`, the same place as today's card where a Bot asks for a secret), with the copy chosen by state:
  - DeepSeek API has no key yet: "This looks like an API key and hasn't been sent. Save it as the DeepSeek API key?" [Check and save] [Send as a normal message] [Clear], small print "Edit it · Save to another provider…".
  - DeepSeek API already has a key: "This looks like an API key and hasn't been sent. Replace the DeepSeek API key with it?" [Check and replace] [Send as a normal message] [Clear], small print as above.
  - Not the DeepSeek format (a DeepSeek key is `sk-` plus 32 hex digits, to be confirmed by testing): "This looks like an API key and hasn't been sent, but it doesn't look like a DeepSeek key. Which provider should it go to?" [Save to a provider…] [Send as a normal message] [Clear], small print "Edit it". [Save to a provider…] opens the add form in DS Bot Settings → Models with the key already filled in (passed only within the page); after saving, `setDraft('')` and the block is removed; if the form is closed without saving, the draft and the block stay.
  - This Bot has a `request_secret` card waiting for a value: "This looks like the key {name} is asking for, and it hasn't been sent." [Put it in that card] [Send as a normal message] [Clear], small print "Edit it · Save as the DeepSeek API key". [Put it in that card] moves the draft into that card's input (scrolling to the card in the chat), `setDraft('')`, and removes the block.
  - [Check and save] / [Check and replace]: takes the value from the draft and runs exactly the same check and save as the setup card; on success `setDraft('')` clears the draft and the block is removed. On failure both the draft and the block stay, the card shows the check result, and [Send as a normal message] [Clear] and the small print "Edit it" stay: 401 says "DeepSeek doesn't accept this key (401). Make sure you copied all of it, or create a new one.", the main button becomes [Clear], and [Check and save] is gone; cannot connect, 429 or 5xx say the same sentence as in the setup card's "Pasting a key" ("the key isn't saved yet"), with the main button [Try again] and [Save anyway] next to it ([Replace anyway] when there is already a key); after saving, likewise `setDraft('')` and the block is removed. With a zero balance the key is saved, the draft is cleared and the block removed likewise, and the card stays, saying "The key is saved, but the account balance is ¥0.00. Top up before it can be used." [Top up ↗] [Got it]; it folds away only on [Got it]; there are no two ways here, so no [Check the balance again] [Try another way]. The setup card depends on state (section 8) and is not written here.
  - [Send as a normal message]: first marks this draft as "let through", removes the block, then calls the conversation input's own send (`ctx.conversation.input.for(conversation).submit()`, the same path as the send button): DSH clears the draft, attachments go along, and if the send fails DSH restores the draft. DSH clearing the draft on send does not count as a change: while the draft is empty, or back to this same text, the "let through" holds, so a restored draft gets no block again; when the draft becomes other non-empty content, the "let through" is void and the new draft is judged afresh. This path does not take DSH's interject settings; while a turn is running, it always queues.
  - [Clear]: `setDraft('')`, removes the block; the key is neither saved nor sent. It is also the way out after a 401.
  - "Edit it": removes the block, leaves the draft as it is, and puts focus back in the input (`focus()`); this draft is marked "let through" and no longer stopped; a "let through" recorded this way is void as soon as the draft changes (unlike the one [Send as a normal message] records), and the new draft is judged afresh.
  - A conversation has only one block (`ctx.conversation.blocks.set` replaces, and passing `undefined` clears the whole block), and the "no usable model" lock below and the onboarding lock of section 6 use it too. So the plugin computes this conversation's block in one place only: model lock > onboarding lock > key block, and clears it only when none of the three applies. "Removes the block" above means dropping the key layer and recomputing by this rule.
  - While the block is attached the input is read-only (DSH's block makes the editor non-editable, and the reason in the placeholder only shows while the draft is empty), so the user cannot change the draft, and every way out is on the card; when something else changes the draft to other content (another plugin calls `setDraft`, for example), the block and the card go away by themselves; after switching to another conversation and back, or after a reload, it judges afresh by the draft and "let through" at that time. "Let through" is kept per conversation in the page's memory and records the full draft; it survives switching away and back, and is gone after a reload. Only a draft that is wholly a key is stopped: a key inside a sentence is not stopped, and DSH's mask only changes the display, so the model still receives it.
  - While stopped, the key stays in this page only: it goes to the Host's `provider-key` only after [Check and save]; after [Send as a normal message] it enters the chat record and goes to the model like any other message. But DSH already stores each conversation's draft in the browser's localStorage (`dsh.conversation.<conversation>`; under `%APPDATA%\DS Bot` in the desktop app, in the user's browser profile in DSH Web), so while the block is attached the key is there too, and it survives a restart until the draft is cleared.
- **Zero account balance** (after sign-in): "You're signed in to DeepSeek, but the balance is ¥0.00. Top up and I can start; one round of chat usually costs only {measured value}, see DeepSeek's price page." [Top up ↗] [Check the balance again] [Try another way]. A key with zero balance uses the card in "Pasting a key" above. While either card shows, it rechecks automatically when the window comes back to the front and every 10 seconds (for up to 10 minutes), and moves on by itself as soon as the balance arrives.
- **Automatic model choice** (whether the plugin forms do the same is open): when only one provider is usable, the user is no longer asked to choose; it uses DSH's default model directly (if usable), otherwise the first model of this provider. Before choosing it checks that it works: with a check that does not call the model it uses that (the account balance, `/user/balance`; whether the latter is billed is not documented), otherwise it sends one 8-token test call. On success the card folds into one row "Connected to DeepSeek-V4.1-Flash · DeepSeek account　Change", followed at once by the Main Bot's fixed opening message, which does not call the model (section 6). This check is still done: the opening message no longer needs the model, but the check also guards the Main Bot's first normal turn. When two or more providers are usable, the user still chooses, grouped by provider, with DSH's default model marked "Recommended".
- After a DeepSeek account sign-in, DSH's account front end tries its best to store the account model as the default, but this step is not guaranteed to finish or to come before us, so when the account is the only provider left, DS Bot picks the account's first model itself without waiting for DSH.
- The opening message is only sent after it is confirmed usable. The chat record never starts with a line of red text.
- When there is no usable model and the model list is known, the Bot chat's input is unavailable, with the placeholder "Connect a model above, and I can reply to you" (DSH's documented `ComposerBlocks`).
- If a message is sent before a model is connected anyway (from another entrance, for example), the opening message is no longer deleted: once a model is connected, the Main Bot first answers this message, then says in one sentence that it manages the team (written by the model, as today). This is its first normal turn, with its usual tools, not counted in the 3 requests of section 6's onboarding; the Session already has a message the user sent, so the onboarding counts as over (section 8), and the fixed opening message and the goal card no longer appear.
- Judging "usable": models marked `needsKey` in the catalog do not count as usable. The Host's default model (`pickDefault`, `defaultModel`, `cachedDefault`), creating Bots, the fallback when `create_bot` names no model, the fallbacks in `desiredModel` and `memory.js` when a model is no longer served, the model menu (`ModelRows`) and the model choice card all pick only from usable models. Models that need a key show "API key needed" in the list, and clicking one opens the key card.
- `needsKey` only covers providers where "the profile sets `apiKeyEnv` and the credential is not configured"; sign-in providers such as the DeepSeek account are never marked `needsKey` and are in the list even when signed out. So "usable" is finally decided by the checks above, and `needsKey` is only the first filter.
- Provider display names: `deepseek-account` shows "DeepSeek account", `deepseek-official` shows "DeepSeek API". The Chinese uses `提供商` ("provider") throughout (replacing `服务商` ("service provider") in `i18n.js`).

### 6. The first useful reply

Once a new team (not an imported one) has connected a model, the Main Bot's chat first goes through two guided steps, then the first task. Every step is a card the plugin draws, and it stays in the chat once answered: the controls turn grey, and the choices made stay highlighted. Every card has "Skip setup, start now", which ends the onboarding. The input is locked (`ComposerBlock`, placeholder "Answer in the card above first") until the onboarding ends or "Say it myself…" on the first-task card is clicked. Imported teams skip all this; they get section 4's "Copied" card and the model check.

- **Opening message**: after the setup card folds into the row "Connected to DeepSeek-V4.1-Flash · DeepSeek account　Change", the Main Bot sends a fixed text in the interface language, "Hi, I'm {name}, and I run your Bot team. What should I do first? Pick below, or say it in your own words.", without calling the model: the opening message still goes into the Main Bot's Session as a turn, and the plugin answers it with this text directly in its `llm/stream` listener, as it answers `HANDOFF_ACK` today on a part change. Below it, as before, a row "Working folder: `C:\Users\<user>\DS Bot`　Change". About 420 ms after the setup card folds into a row comes the opening message, and at about 900 ms the goal card.
- **Goal card**: title "What should the team help you with first?", with a grey "Pick any" on the same line.
  - The four options [Writing: articles, weekly reports, copy] [Writing and fixing code] [Looking things up, research] [Daily chores: calendar, email, tidying] are toggle buttons (`aria-pressed`, in a group labelled "What to do first, pick any"): one click selects, another deselects, and several can be selected; selected ones carry a check mark, not only a color.
  - One input "In your own words…".
  - [OK] is the only main button on the card and can be clicked only when at least one option is selected or the input has text; Enter in the input means [OK], except while an input method is composing.
  - [Skip]: creates no Bot and goes straight to the first-task card, with the three fixed tasks of the old "Try:" on it: "What can you do for me?", "Create a Bot that writes my weekly report", "Search today's tech news and tell me about 5 stories". These three need no file reads, commands or calendar permission, and do not depend on the model to make up a task.
  - After the answer the selected options stay highlighted, all controls turn grey, and the text in the input stays; when [Skip] or "Skip setup, start now" was clicked, no option counts as selected.
  - Options only: no model call; ready-made suggestions appear at once (one set per goal, written in the code).
  - Text in the input (with or without options): one model call. It is a JSON call without tools, of the same shape as the context steward's `askSteward` (a fixed prompt, no `tools`, through `ctx.llm.stream`, answering only JSON); this call has its own limits, `maxTokens` 700 and a 12-second timeout, and the answer is validated against a closed schema; if it does not fit, it counts as no response. The schema holds `goal` (one of `write`, `code`, `research`, `daily`, `general`: one for each of the four options, plus the general set), a summary of at most 18 characters, at most 3 Bot drafts (name, role, reason) and at most 3 first tasks (each with the index of its draft).
  - When the whole input is one key (same rule as "A key pasted into the chat is recognized too" in section 5), [OK] does not call the model, and section 5's card appears below the goal card (copy and buttons chosen by state, without [Send as a normal message] and "Edit it"); after saving or [Clear] the input is emptied, and the goal card waits for the user to answer again. The input can still be edited; as long as the whole input is still one key, [OK] does not call the model.
- **Merging**: the selected goals are ordered as on the card, not in the order clicked. With text, the text's set is the model's drafts, and which goal it belongs to follows the `goal` the model returns (when the model does not respond, the text is matched by keywords to a ready-made set, see "When the model is unavailable" below): when `goal` is one of the selected goals, that set is replaced by the model's drafts in the same position; when it is a goal not selected, it is appended; when it is the general one and options are selected, it is not added (with text only, the text's set is used, general included). With one goal it is that goal's set. With several goals the Bots are taken in turn: first the first of each set, then the second of each set, and so on, keeping only one of each name, at most 5; the first tasks are each remaining Bot's own task (the model's tasks are assigned to Bots by their draft index), in Bot order, at most 3. In the summary each goal is one word (writing / code / research / daily chores, with no `、` (the Chinese list comma) inside a word), and several goals are joined with `、`; the quoted part is the user's own words, replaced by the model's summary when longer than 18 characters:
  - Options only: "You'd like to start with writing and research: I suggest these N Bots; you can change the names right here."
  - Options plus text: "You'd like to start with writing, and also said "check the competitors": I suggest these N Bots; you can change the names right here."
  - Text only: "Going by what you said, "…", I suggest these N Bots; you can change the names right here."
- **Suggestion card**: below the summary, one row per Bot: a checkbox, its whale (each in its own color), an editable name (at most 12 characters), a role label (at most four characters), and a one-sentence reason.
  - [Create these N Bots] is the main button; N follows the ticks, and it cannot be clicked when none is ticked; the name in [Only {first name}] follows the name in the first row.
  - [Other suggestions]: calls the model again (the same call and schema), with the selected goals, the user's words and the drafts already given in the prompt, asking for a set without repeats, replaces the rows on the card, and the summary says "Another set: I suggest these N Bots; you can change the names right here.". The goal card and the suggestion card together allow at most 3 requests; when reached, this button greys out with "Limit reached" next to it; the bottom of both cards says "Model requests n/3".
  - "Skip setup, start now".
- **Creating Bots and the first task**: only clicking [Create…] really creates them, and these Bots appear one by one under the Main Bot in the sidebar with the edited names. They send no model-written greeting: each Bot's chat first has a fixed text, its name plus the reason from its row on the suggestion card (such as "Hi, I'm Quill. I draft articles, weekly reports and copy, and revise them in your voice."), answered in the `llm/stream` listener like the Main Bot's opening message, so [Create…] costs no request. Then comes the first-task card "What should we do first?": the three tasks from the suggestions, with the names the user gave (when Bots are unticked and there are fewer than three tasks, the three fixed tasks above fill it up), plus "Say it myself…" (opens the input and puts focus there). Clicking a task is the same as the user sending that sentence. As soon as the first task (the clicked task, or the first message sent after "Say it myself…") is sent, the plugin calls the release function `restrict` returned and removes the guard: it is the Main Bot's first normal turn, with its usual tools, not counted in the 3 requests and not bound by the per-step tokens and time limits below. After it replies, a grey line "Onboarding done: {name}'s tools are no longer limited" appears in the chat, and the input opens. "Skip setup, start now" lifts the limits directly, shows this grey line and opens the input.
- **When the model is unavailable**: options still give the ready-made suggestions. With text in the input, the suggestion card says above it "The model isn't responding right now. Use the ready-made suggestions, or just start.", with the ready-made suggestions below (the text matched by keywords to a ready-made set, then merged by the rules above), and the summary says only "I suggest these N Bots; you can change the names right here."; when [Other suggestions] gets no response it shows the same sentence, the rows stay, and the request still counts. When the reply to the first task fails, it is the fix card below.
- **The depth limit is a mechanism, not a prompt**:
  - The step table is written in code; the Host moves on by the card's answers, and the model never picks the next step.
  - During the onboarding (from the opening message until the first task is sent), the first Main Bot's Session keeps only `ask_user` and `create_bot` in draft mode (drafts only, created only when the user clicks) via `agent.ctx.tools.restrict({ allow })`, and `tools.guard` limits the number of calls per step; beyond that it refuses and asks it to answer directly. It is lifted as soon as the first task is sent (above).
  - Each step (each press of [OK] or [Other suggestions]) allows at most one request, with 400 to 700 output tokens (`maxTokens` 700): no first token within 8 seconds, or not finished by 12 seconds, brings this step's fallback card. If a turn does run in the Main Bot's Session during the onboarding (the input is locked, so it can only come from another entrance), it also gets only one request, must have its first token within 8 seconds and finish the whole turn within 20 seconds, or the fallback card appears likewise. The whole onboarding allows at most 3 requests, which is the "Model requests n/3" on the card; the first task is not counted, since the limits are lifted when it is sent.
  - Every step has a card that works with the model switched off. CI runs these cases with the mock model: normal, network down, going round in circles, off-topic answers, invented model names, 401, zero balance, a key pasted into the goal card's input.
- Any failed turn in a Bot chat gets a fix card drawn by the plugin, replacing DSH's "This turn failed" line (DSH Agent's normal Sessions are unchanged). The raw text, code, HTTP status code and request id go in "Technical details" and can be copied; the raw text of AUTH is still not shown.

- The card is chosen by the failure code, not the raw text (DSH also routes by code; the raw text and `failureMessage` are its internal details). - "Try again" makes the Bot go on, without sending the user's words again. After a top-up it rechecks the balance by itself and goes on.
- A Bot's greeting (except the first Main Bot's fixed opening message and the fixed greetings of Bots created from the suggestion card, which do not call the model) that fails on credentials or balance is kept back and sent at the next passing check.

### 7. The first hour

- **The command sandbox cannot start commands** (#523, `exit code 3221225794`, a DSH problem): below the tool result it shows "On this computer, the DeepSeek Harness sandbox can't start commands (error 0xC0000142). It's not a problem with the command itself. You can give {name} "Full access", or approve single commands when it asks." [Open {name}'s permission settings] [Not now]. Giving full access still needs a second confirmation and is still marked red. The Bot also gets a note telling it to ask for approval instead of retrying blindly.
- On Windows without PowerShell 7, the prompt states that commands run in Windows PowerShell 5.1: `&&` and `||` cannot be used.
- **System proxy** (desktop app only; whether it is on by default is open): when the user has not set `http_proxy` / `https_proxy` / `all_proxy` (in any case) and the `.env` in the data location does not have them either, the app reads the Windows system proxy with `session.resolveProxy` and passes it to the engine as its start environment.
  - `resolveProxy` returns Chromium's list of PAC results (separated by `;`, possibly `PROXY`, `HTTPS`, `SOCKS`, `DIRECT`): it takes the first usable entry in order and stops at `DIRECT`; `PROXY h:p` is written as `http://h:p` and `HTTPS h:p` as `https://h:p`, always with the scheme (DSH does not accept `h:p` without a scheme); SOCKS is skipped (DSH does not support it either), and the hint changes to "The system proxy is a SOCKS proxy, which DS Bot can't use. Turn on an HTTP port in your proxy software, or set https_proxy."
  - `NO_PROXY` is not set: DSH itself sends local addresses direct, and on Windows only one of the environment variables with the same name in different case is passed, so setting it could override the user's `no_proxy`. PAC can give different answers for different hosts; resolving for `api.deepseek.com` is only an approximation.
  - The proxy variables go only into the start environment, never into the `.env` of the profile folder (DSH refuses proxy variables there). The app's own update downloads go through Chromium's network stack, which follows the system proxy anyway and is not affected by this.
  - Settings → General → Network has a switch "Follow the system proxy"; when it is on, the current system proxy (such as 127.0.0.1:7890) shows next to it. "Can't reach GitHub" gets one more sentence about the proxy.
  - `NODE_USE_SYSTEM_CA` is set in the engine's start environment only after it is verified to work under `ELECTRON_RUN_AS_NODE`; if that cannot be verified, it is not set.
- The Bot list is not empty on a cold start (#559): after the first mount it checks whether the team sidebar really came up, and if not it mounts once more; the "back to the Main Bot" logic moves out of `TeamSidebar`.
- Closing the window while Bots are still working first asks "2 Bots are still working. Closing the window will stop them." [Close anyway] [Cancel] (#500).
- The whale menu gets "Models and API keys", and "Sign in to DeepSeek" when signed out. "Classic Agent mode" is in the whale menu (since 2026-11-11, see §8), and also in Settings → General → Mode.

### 8. Later starts and ways back

- Every later start shows the start page too, looking the same as the first start: the 112 px whale and the ring of three arcs, no text when all goes well and no location row, except when the drive holding the data has only a fifth of its free space at the start left: then there is a location row, and [Change the location…] moves the data on the spot, with the confirmation and "That place won't work" asked on the card, not in a system dialog ([Start window](2026-10-26-start-window.md) sections 5 and 6); from 45 seconds the whale says "Slower than usual, please wait a little longer", and the hint row has only [Open the log folder]; at 180 seconds it is the same as the first start; when ready there is no celebration, the ring closes, and the whale jumps straight onto the Main Bot's avatar in the sidebar, or dives when there is nowhere to land ([Start window](2026-10-26-start-window.md) sections 5 and 8). Then it opens the last Bot (expected 3 to 12 seconds; later starts have not been measured yet).
- The setup card depends on state: when there is no usable model (skipped, key deleted, signed out), the Main Bot's setup card comes back; when the account sign-in has expired it shows "The DeepSeek account sign-in has expired." [Sign in again] (in the desktop app this also signs in in the sign-in window).
- The goal card, the suggestion card and the first-task card (section 6) appear only when a new team has connected a model and the onboarding is not over yet.   - Only folders the app created itself are moved. The reopened process starts at the new place from this record, `DS_BOT_WORKSPACE` points to `R\workspace`, the plugin registers it on the next turn, and Bots and groups that use the team workspace change to a new part as usual; `locations.json` is written only after the new engine is `ready`, then the old data folder is deleted (in the copy branch; with the marker the whole folder, without it only the entries on the list), and the record turns into "the team workspace is still moving". ### 9. Uninstall and reset

- Uninstalling first shows NSIS's "Are you sure you want to uninstall", then asks only one more question, defaulting to "No": "Also delete DS Bot's data? This deletes chats, Bots, memory, API keys and sign-ins: {data location}, and {shell data}. If DS Bot created the data folder, it is deleted as a whole; otherwise only DS Bot's own files are deleted. The Bots' work folder {team workspace} is not deleted (it holds your files). Choose "No" to keep everything and carry on after reinstalling."
- On "Yes": when the data folder has the `.ds-bot` marker it is deleted as a whole; without the marker (installed by an old version, or `D:\` or a non-empty folder that the old first start allowed) only the app's and DSH's own entries are deleted (`bot`, `profiles`, `sessions`, `attachments`, `storages`, `.anonymous-user-id`, `.credentials.yaml`, `.env`, `.import-*`, `.import-check-*`), and the folder itself is deleted only when it is empty afterwards. The staging folder for changing the data location is next to the data folder (`.<folder name>.moving-*`), not inside it. The drive root, the home folder and the team workspace are never deleted. Then `%APPDATA%\DS Bot` and `%LOCALAPPDATA%\ds-bot-updater` are deleted.
- A silent uninstall (`/S`, winget included) and the uninstall during an update (the old uninstaller runs with `/S --updated`) ask nothing and delete nothing (CI's existing "data still there after uninstall" check still passes).
- In one-click install mode, the uninstaller is already set to silent before `customUnInit`, and `${Silent}` cannot tell the user's `/S` from a normal uninstall, so what really counts is parsing `/S` and `--updated` from the command line again; with either one it asks nothing. The question uses a MessageBox without `/SD` (with it, the box never shows in one-click mode), with `MB_SETFOREGROUND`, since there is no uninstall window to attach to at that point. The text uses its own LangString defined for LCID 1033 and 2052 (when `installer.nsh` is included, constants such as `${LANG_ENGLISH}` are not defined yet). The template order is an internal detail of electron-builder; when it is upgraded, CI's interactive uninstall test guards it.
- README.md gets an "Uninstall and reset" section that writes out the real places on Windows with `%APPDATA%`, `%LOCALAPPDATA%` and `%USERPROFILE%`.

## What DSH needs to provide

We do not patch; we ask DSH for the following:

1. A documented switch to turn off the web version's "Preview notice" (next to `credentialOnboarding`), for apps that embed it.
2. Fix the `0xC0000142` when the Windows sandbox starts pwsh inside Electron (`ELECTRON_RUN_AS_NODE`) (#523 has a reproduction), and report a structured error code, not only the exit code.
3. `MISSING_CREDENTIAL` shows a localized sentence in the chat, not the raw text of the provider route and the environment variable; the failure nodes of AUTH and QUOTA carry the HTTP status code (without the key).
4. Declare the actions injected by the `settings.models.sign-in` entry (`start`, `cancel`, `showLogin`, `setOnboarding`, `refreshAccount`, `hooks.account` and so on) and `credentialOnboarding` as plugin interfaces stable across versions, or provide a documented client API to "start the DeepSeek sign-in and read the balance".
5. A credential check that costs nothing and does not need the plugin to read the key back (`ok / invalid / no-balance / unreachable`), and a live check in the key field of the model page.
6. `listModels` marks which models' providers have no credentials yet (a follow-up to PR #316).
7. A top-up button on the web version's low-balance message (today it is only a toast when there is no `nativePlatform`); this message can be told apart by Session, or the plugin can take over its own Sessions.
8. The sign-in done page tells the user to go back to the original app; when the app is already closed and the callback address is void, it gives a clear message.
9. Make DSH's proxy follow the Windows system proxy (PAC included), and consider trusting the system certificate store.
10. The `settings.launcher` slot can open a given section of the settings directly (such as "Models"). Today this can be done with a detour through our own `settings.onboarding` step (see section 8); this interface would make it simpler.
11. `runProfile` reports named start stages, for the shell to show real progress.
12. The pwsh tool's description states whether it is really Windows PowerShell 5.1 or PowerShell 7.
13. A documented hook before sending (or `ComposerBlocks` that can carry a card), so a plugin can stop a message that is only a key before it enters the chat record; today it can only watch the draft and then attach a block, which cannot stop a paste and Enter at the same instant.
14. The web front end (or the Desktop bridge) provides a way to "hand the authorization page to the host's own window"; today the desktop app can only catch the `about:blank` of the web front end's `window.open` and watch where it navigates.

## Not done

- No separate welcome wizard in the app for setting up models: models are set only in the Main Bot's setup card and in DS Bot Settings → Models. The goal card, the suggestion card and the first-task card are also cards the plugin draws in the Main Bot chat, not an app wizard.
- During the onboarding the model does not pick the next step, nor call tools round after round by itself: the step table is in code and moves on by the card's answers, and the Main Bot's tools are limited until the first task is sent (section 6). When only options on the goal card are selected, the model is not called.
- The whale's line is never a paragraph: it says one sentence only when the user needs to know or answer, fitting on one line; in a smooth start the start page has no text, no explanation paragraphs and no rotating tips.
- The clipboard is not read outside the time the setup card shows; keys from the clipboard and from DeepSeek Harness are never saved automatically: the user always clicks a button, and the key is then checked and saved by the "Pasting a key" rules.
- The existing key on the setup card only covers keys, and does not move the account sign-in in DeepSeek Harness on its own (the grant records belong to DSH's account module, and the app does not write them): people who did not import a team, or answered [Don't copy yet], and who signed in with an account in DeepSeek Harness, sign in once more in the sign-in window. When a team is imported, `.credentials.yaml` is copied as a whole (except when the target already has the user's own key or sign-in), the account sign-in comes along, and there is no need to sign in again.
- We do not pretend to be `dshDesktop`, and do not use CSS or the DOM to hide or change DSH's interface; DSH's "Preview notice" waits for its switch. Nor do we write its "read" version number in advance (`welcomeNoticeVersion` of `ui-settings-general`): that would click "Continue" for the user, the version number is not exported publicly, and writing it in the patch layer would also make saving fail when the user later clicks "Continue".
- We do not change DSH or depend on files inside a DSH install. Of DSH's internal interfaces we use only the ones already in use, `@deepseek-ai/dsh-app-boot`, `@deepseek-ai/dsh-session-format`, `@deepseek-ai/dsh-session-format-catalog` and the actions injected by the `settings.models.sign-in` entry (the setup card also calls `setOnboarding`, `showLogin`, `cancel`, `refreshAccount`, see "Known limits"), and add no new ones.
- No scanning of drives on every start: fixed drives are listed only once, when the drive is too full or the default location cannot be used; card readers, USB sticks, removable hard drives, network drives and optical drives are never touched and never suggested.
- The uninstall never deletes the team workspace, the drive root or the home folder.
- Keys, tokens and real user paths never appear in logs, copied details, diagnostics files or docs; locations in the interface are shown only to the user. Screenshots use only throwaway folders.
- No text, icons or illustrations from other products (including the welcome page illustrations and fonts of DSH Desktop); the trust notes use diagrams we drew ourselves.

## Known limits

- Until DSH adds the switch, the "Preview notice" is still the first screen of the engine's page, and the user has to click "Continue" once more; it appears again for every new data folder (later imports, starting over). The start page does not mention it in advance (section 3).
- The setup card calls the actions injected by the `settings.models.sign-in` entry. They have type declarations, but DSH did not write them as an interface for plugins, and they may change between rc versions. When one is missing it falls back to today's `DeepSeekSignIn`; every upgrade of the pinned DSH needs a retest (see also "What DSH needs to provide", item 4).
- If the id of the `credentialOnboarding` line is renamed in DSH, the patch only leaves a warning and stops working silently; the check on `__DSH_MODELS_ONBOARDING__` in Acceptance catches it.
- `GET /user/balance` is not part of the chat API, and whether it is billed is not documented; it proves the key and the balance, not whether the model can be used. Failures other than 401 do not stop the user; the fix card of the first turn is the fallback.
- When choosing a model automatically, providers without a check that does not call the model need one extra 8-token test call.
- The opening message is fixed text and costs nothing, but it also cannot say anything only the model would know.
- The model's step in the onboarding is slower than a card: a real network round trip, and in the worst case the fallback card comes only after 12 seconds (the first token came within 8 seconds, then it stalled); it costs money first (only when the user wrote text or asked for another set) before showing any effect; the wording differs every time, and CI can only test the structure.
- The merged first tasks lean toward the first two goals: with three or more goals, the later goals get no first task; when earlier Bots are unticked, the three fixed tasks fill up the card instead of later Bots' tasks (how to split them is in "Open questions").
- On the first start the main window shows only about 1.2 seconds after ready (before, about 620 ms), and on later starts about 0.7 seconds (before, 120 ms): the extra time is mainly the roughly 460 ms of waiting for the text and the ring on the page to fade before growing.
- When the balance is too low in a Bot chat, DSH's own balance message (not per Session) appears together with the fix card.
- The Chinese default name follows the interface language of the first request; while DSH's stored language preference has not finished loading, it may still be the browser's language, so with an English browser and DSH set to Chinese, a new team may still be called Chief. In the desktop app, a brand-new data location follows the system interface language.
- When falling back to signing in in the system browser, Windows' foreground rules may not let the window come to the front after sign-in; then only the flashing taskbar button and the card's own "signed in" state are left.
- The sign-in window relies on the DSH web front end's practice of "open `about:blank` first, then navigate to the authorization page", which is not an interface; if DSH changes it, it falls back to the system browser (see also "What DSH needs to provide", item 14). A flow where the main frame leaves the DeepSeek domain in the sign-in page (third-party sign-in, for example) moves to the system browser and starts again from the authorization page, and anything half filled in the sign-in window is not carried over.
- The sign-in window does not keep the DeepSeek platform's sign-in state, and [Top up ↗] (on the zero-balance card and the ACCOUNT_QUOTA fix card) still opens the platform in the system browser: people who have not signed in to the platform in the browser (such as a new account just registered with a phone number in the sign-in window) must sign in there once more. Signing in in the browser used to skip this step (whether to change it is in "Open questions").
- The fix cards and the whale menu use DSH's own sign-in box, which still says to continue in the browser while the sign-in window is open: this is DSH's copy, and we do not change its interface. Clicking [Cancel] or × in that sign-in box cancels this sign-in, and the sign-in window closes with it.
- The clipboard is read only while the setup card shows, but there is no notice when it is read; the first eight characters in the card's row are the evidence that it was read.
- A chat draft that is only a key is caught by watching the draft and then attaching a block, so a paste and Enter at the same instant (scripts, automation) may send it before the block; a key inside a sentence is not stopped, and DSH's mask only changes the display.
- A chat draft that is only a key stays in the browser's localStorage until it is cleared; this is how DSH stores drafts. On a 401, or when the user ignores the card, the key stays with the draft until the next start. The plugin clears it with `setDraft('')` only on saving, [Put it in that card] or [Clear]; on [Send as a normal message] DSH clears it after sending; the plugin does not delete drafts for the user.
- Before signing, Windows 11 with Smart App Control on cannot install the unsigned installer, and the only way is the DSH Desktop plugin first. If the signing entity is SignPath Foundation, the publisher shows its name.
- The one-click install drops choosing the program folder (estimated at about 600–700 MB on drive C, to be written into the README after measuring); only `/D=` is left.
- Some NSIS errors built into electron-builder (failing to uninstall the old version, failing to extract) are in English only.
- Deleting data at uninstall cannot be undone; for folders without the marker only known entries are deleted, so an incomplete list only leaves files behind and never deletes too much.
- Following the system proxy may send DeepSeek traffic through a proxy the user forgot about or has already quit; the diagnostics and the fix card name the proxy, and it can be turned off.
- Whether `NODE_USE_SYSTEM_CA` works under `ELECTRON_RUN_AS_NODE` is not verified; if it cannot be verified it is not set, and company networks with TLS inspection still cannot connect, only with a clearer message.
- After an import, the Main Bot's early part change reads the recent chats once to write the handoff note, which costs many tokens with a cold cache (#384 measured 170,000 tokens).
- The suggested drive excludes USB, SD and virtual drives by bus type, but a removable hard drive reported as a fixed drive may still be suggested; on machines where PowerShell is blocked by policy there is no suggested drive, only "Another location…".
- After [Move to…], the old team workspace the app created is gone (renamed or moved file by file), so DSH Agent's Sessions have to pick a folder again; Bot and group Sessions change to a new part and are not affected. A team workspace the user picked is not moved, so after the move both it and `R\workspace` exist: the team switched folders, it is not taking space twice.
- A team copied from DeepSeek Harness takes space on both sides: the app never writes `~/.dsh`, so it cannot delete the originals for the user, and can only state the extra space in the card and in Settings.
- On file systems without hard links (FAT, exFAT), the background copy of work files falls back to "check once, then rename", and a file of the same name that a Bot creates between the check and the rename is overwritten.
